# 调试与错误恢复

## 概览

使用结构化的五步方法调试问题：复现、定位、简化、修复、防护。好的调试是系统的科学，而不是随机的猜测。

## 何时使用

- 测试失败时
- 构建中断时
- 行为与预期不同时
- 用户报告 bug 时
- 你需要诊断和修复问题时

## 五步分诊

### 第 1 步：复现

在修复之前，你必须能够可靠地复现问题。

```markdown
1. 编写一个演示问题的测试（应该失败）
2. 或记录确切的复现步骤
3. 或创建一个最小复现示例
```

**如果没有复现，就没有修复。** 你不能修复你不能可靠复现的东西。

### 第 2 步：定位

找到问题的根源，而不仅仅是症状。

```markdown
1. 阅读错误消息 —— 它通常告诉你确切的问题
2. 检查堆栈跟踪 —— 它告诉你问题发生在哪里
3. 使用二分法搜索消除不可能的原因
4. 添加日志以追踪执行路径
```

**常见模式：**

| 症状 | 可能原因 |
|------|---------|
| AttributeError | None 引用 |
| 测试在 CI 中失败但在本地通过 | 环境变量、时区、路径分隔符 |
| 间歇性失败 | 竞态条件、共享状态、未排序的集合 |
| MemoryError | 泄漏的引用、无界缓存、大负载 |

### 第 3 步：简化

创建一个最小复现示例，只包含触发问题所需的代码。

```markdown
1. 删除不相关的代码
2. 简化数据，同时保持问题存在
3. 隔离有问题的函数或组件
4. 创建可以在真空中运行的最小测试
```

简化迫使你理解问题，而不仅仅是修补它。

### 第 4 步：修复

实施最小修复以解决问题。

```markdown
1. 实施修复
2. 确认之前失败的测试现在通过
3. 运行完整测试套件以检查回归
4. 审查修复以确保它解决了根本原因，而不仅仅是症状
```

### 第 5 步：防护

添加防护，确保问题不会再次出现。

```markdown
1. 添加或更新测试以覆盖此场景
2. 添加输入验证或断言
3. 添加错误处理以优雅地处理类似问题
4. 如需要，更新文档
```

## 停线规则

如果以下任何情况为真，停止并升级：

- 问题影响生产用户且没有立即可用的修复
- 你在同一个问题上卡了超过 2 小时没有进展
- 问题涉及你不熟悉的系统或代码库
- 修复可能需要破坏性变更

## 安全回退

在应用修复之前，确保你可以回退：

```bash
# 在开始修复之前提交当前状态
git commit -m "checkpoint: 在修复前保存当前状态"

# 如果修复使情况变得更糟，回退
git reset --hard HEAD~1
```

## 调试工具

### 日志调试

```python
# 添加战略性日志以追踪执行
import logging

logger = logging.getLogger(__name__)

def create_task(request: TaskRequest) -> Task:
    logger.debug("[DEBUG] 进入 create_task，参数: %s", request)
    task = task_repository.save(Task(title=request.title))
    logger.debug("[DEBUG] 任务创建后: %s", task.id)
    return task
```

### 断点调试

```python
# 在关键位置设置断点
def process_task(task: Task) -> Task:
    breakpoint()  # Python 3.7+ 内置断点
    # 或使用 pdb
    import pdb; pdb.set_trace()
    return task
```

### 二分法搜索

```bash
# 找到引入 bug 的提交
git bisect start
git bisect bad HEAD
git bisect good <已知良好的提交>
# 在每个中点运行测试以缩小范围
pytest tests/test_task_service.py
```

## 常见合理化

| 合理化 | 现实 |
|---|---|
| "我可以直接修复，不需要复现" | 没有复现的修复是猜测。你可能会修复错误的东西。 |
| "这个 bug 太罕见，不值得修复" | 罕见 bug 通常是严重问题的症状。调查它。 |
| "我可以稍后再调试这个" | bug 不会自行修复。它们会累积技术债务。 |
| "错误消息没有意义，跳过它" | 错误消息通常包含解决方案。仔细阅读它。 |

## 危险信号

- 在复现问题前尝试修复
- 修复症状而不是根本原因
- 没有添加测试来防止回归
- 在不确定时猜测而不是调查
- 忽略错误消息，假设它们是误导性的

## 验证

在调试完成后：

- [ ] 问题可以可靠复现（测试或步骤）
- [ ] 根本原因已识别并记录
- [ ] 修复已实施并通过测试
- [ ] 添加了防护测试以防止回归
- [ ] 完整测试套件通过
- [ ] 构建成功
- [ ] 没有引入新的问题
