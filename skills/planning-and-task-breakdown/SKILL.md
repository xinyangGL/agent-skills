# 规划与任务拆解

## 概览

将规格拆解为小的、可验证的任务，每个任务都有明确的验收标准。好的规划使得实现成为机械性的——每个任务足够小，可以一次完成和验证。

## 何时使用

- 你有规格，需要可执行的单元时
- 功能复杂到需要多个步骤时
- 你开始感到不知所措或不知道从哪里开始时
- 在 specs 编写完成后、实现开始前

## 任务拆解原则

### 1. 小到可以一次性完成

每个任务应该在单个上下文中完成——不需要进一步拆解。

```
好：添加带有验证的任务创建端点
避免：构建任务系统
```

### 2. 可独立验证

每个任务完成后应该有明确的证据表明它已完成。

```
好：添加任务创建测试（测试通过 = 完成）
避免：改进任务处理（"改进"无法验证）
```

### 3. 按依赖排序

任务应按执行顺序排列。任务 N 不应依赖于尚未完成的任务 N+1。

```
1. 定义任务数据库模式
2. 创建任务创建端点（依赖于 1）
3. 添加任务创建测试（依赖于 2）
```

### 4. 包含验收标准

每个任务应明确说明"完成"的样子。

```markdown
- [ ] 添加任务创建端点
  - 接受 title（必填）和 description（可选）
  - 验证 title 非空且不超过 200 字符
  - 返回创建的带有服务器生成 ID 的任务
  - 测试覆盖正常路径和验证错误
```

## 规划过程

### 第 1 步：阅读规格

彻底理解规格。识别主要功能区域。

### 第 2 步：识别主要阶段

将工作分组到 3-7 个主要阶段。

```markdown
## 阶段
1. 数据库设置
2. API 端点
3. 前端组件
4. 测试
5. 集成与验证
```

### 第 3 步：拆解每个阶段

将每个阶段拆解为具体的、可验证的任务。

```markdown
## 阶段 1：数据库设置
- [ ] 创建任务数据库模式
  - 字段：id、title、description、createdAt、updatedAt
  - 迁移脚本可运行且可回滚
- [ ] 添加数据库连接配置
  - 使用环境变量
  - 在 CI 中可运行

## 阶段 2：API 端点
- [ ] 添加任务创建端点
  - POST /api/tasks
  - 验证输入
  - 返回创建的任务
- [ ] 添加任务列表端点
  - GET /api/tasks
  - 支持分页
  - 支持按状态过滤
```

### 第 4 步：估计复杂度

为每个任务标记复杂度，以识别可能需要进一步拆解的任务。

```
S（小，< 30 分钟）：添加任务创建端点
M（中，1-2 小时）：添加任务列表端点，带过滤
L（大，> 2 小时）：实现实时协作 ← 需要进一步拆解
```

任何 L 大小的任务都应该被拆解得更小。

### 第 5 步：识别风险

标记可能阻塞实现的风险和未知因素。

```markdown
## 风险
- 数据库迁移在 CI 中需要特殊设置
- 分页 API 需要与前端团队协调
- 实时功能需要 WebSocket 基础设施（尚未存在）
```

## 输出格式

```markdown
# [项目名称] 实施计划

## 概述
[1-2 句话的项目描述]

## 阶段 1：[名称]
- [ ] [任务 1]
  - 验收标准：[具体]
- [ ] [任务 2]
  - 验收标准：[具体]

## 阶段 2：[名称]
...

## 风险
- [风险 1] — [缓解策略]

## 依赖
- [列出任何外部依赖]
```

## 常见合理化

| 合理化 | 现实 |
|---|---|
| "我可以直接开始，这很简单" | 没有计划，你会在不了解依赖关系的情况下开始工作。计划防止返工。 |
| "计划会很快过时" | 计划是指导，不是承诺。但根本没有计划更糟——你在真空中工作。 |
| "任务太小了" | 小任务是可以管理的。大任务是隐藏的惊吓。 |
| "我知道该做什么" | 直到你开始并发现依赖关系比你想象的要复杂。计划表面化依赖关系。 |

## 危险信号

- 任务大到无法一次性完成
- 任务没有验收标准
- 任务按任意顺序排列，而非依赖顺序
- 计划没有识别任何风险
- 计划存在于用户脑海中，而非文件中

## 验证

在规划完成后：

- [ ] 每个任务都可独立验证
- [ ] 任务按依赖顺序排列
- [ ] 每个任务都有验收标准
- [ ] 复杂度已估计，大任务已进一步拆解
- [ ] 风险已被识别
- [ ] 用户确认了计划
