# 代码审查与质量

## 概览

通过五个维度审查代码——正确性、可读性、架构、安全性和性能。好的审查使得代码库随着时间的推移而改善，而不是仅仅防止 bug。

## 何时使用

- 在合并任何变更之前
- 用户要求审查代码时
- 审查 PR 或代码变更时
- 在发布前进行最终质量检查时

## 五维审查框架

### 1. 正确性
- 代码是否按规范/任务要求那样工作？
- 是否处理了边界情况（null、空值、边界值、错误路径）？
- 测试是否真正验证了行为？
- 是否存在竞态条件、差一错误或状态不一致？

### 2. 可读性
- 其他工程师能否无需解释就理解这段代码？
- 命名是否具有描述性且与项目约定一致？
- 控制流是否清晰（没有深层嵌套的逻辑）？
- 代码是否组织良好（相关代码分组、边界清晰）？

### 3. 架构
- 该变更是遵循现有模式还是引入了新模式？
- 如果是新模式，是否有合理理由并已文档化？
- 模块边界是否得到维护？
- 抽象层次是否恰当（不过度设计、不过度耦合）？

### 4. 安全性
- 用户输入是否在系统边界处经过验证和清理？
- 密钥是否远离代码、日志和版本控制？
- 是否在需要的地方检查了认证/授权？
- 是否有任何具有已知漏洞的新依赖？

### 5. 性能
- 是否存在 N+1 查询模式？
- 是否存在无界循环或无约束的数据获取？
- UI 组件是否存在不必要的重渲染？
- 列表端点是否缺少分页？

## 变更大小

目标 ~100 行/PR。超过 ~1000 行应该被拆分。

```
~100 行  → 易于审查，易于回滚
~300 行  → 对于单一逻辑变更可以接受
~1000 行 → 拆分成更小的变更
```

## 严重性标签

对每个发现进行分类：

**Critical（严重）** —— 合并前必须修复（安全漏洞、数据丢失风险、功能损坏）

**Important（重要）** —— 应在合并前修复（缺少测试、错误的抽象、差的错误处理）

**Suggestion（建议）** —— 考虑改进（命名、代码风格、可选优化）

**Nit（小问题）** —— 琐碎的，可以在之后修复

**FYI（仅供参考）** —— 无操作，仅提供信息

## 审查速度规范

| PR 大小 | 最大审查时间 |
|---------|-------------|
| < 100 行 | < 2 小时 |
| 100-300 行 | < 4 小时 |
| 300-1000 行 | < 8 小时 |
| > 1000 行 | 应该被拆分 |

如果审查需要更长时间，变更可能太大了。

## 拆分策略

当变更太大时，按关注点拆分：

```
原始：重构认证模块
拆分：
1. 提取验证逻辑到共享工具
2. 更新会话处理
3. 添加速率限制
4. 更新测试
```

## 审查输出模板

```markdown
## 审查摘要

**结论：** APPROVE（通过） | REQUEST CHANGES（要求修改）

**概述：** [1-2 句话总结变更和整体评估]

### 严重问题
- [File:line] [描述和建议的修复]

### 重要问题
- [File:line] [描述和建议的修复]

### 建议
- [File:line] [描述]

### 做得好的方面
- [正面观察 —— 至少包含一条]
```

## 规则

1. 先审查测试 —— 测试揭示意图和覆盖率
2. 在审查代码前先阅读规范或任务描述
3. 每个严重和重要发现都应包含具体的修复建议
4. 不要批准存在严重问题的代码
5. 认可做得好的方面 —— 具体的表扬能激励良好的实践
6. 如果你不确定某件事，请说明并建议调查，而不是猜测

## 常见合理化

| 合理化 | 现实 |
|---|---|
| "这太简单了，不需要审查" | 简单的变更也会引入 bug。审查防止回归。 |
| "我会稍后审查" | 稍后意味着从未。在合并前审查。 |
| "我已经审查过了，没问题" | 审查不是一次性的。每次变更都需要审查。 |
| "审查减慢了我的速度" | 没有审查的速度是幻觉。你最终会花更多时间修复 bug。 |

## 危险信号

- PR 超过 1000 行
- 没有测试或测试不充分
- 混合了格式化和行为变更
- 安全敏感代码没有经过专门的安全审查
- 审查者对代码库领域不熟悉

## 验证

在审查完成后：

- [ ] 所有五个维度都已评估
- [ ] 严重问题已修复
- [ ] 重要问题已解决或已标记
- [ ] 测试已审查并通过
- [ ] 构建已验证
- [ ] 审查者明确批准或要求修改
